# Hook acknowledgement evidence

Baseline `f28f8edfcb2972ac322f4f12b1f224226a9a40ab` runs automatic Codex and Claude Code recall/capture in separate Python processes. Both native adapters accept a positive `position` as sufficient capture acknowledgement before flushing. The HTTP contract instead requires `status: accepted`, an exact Source reference, and a positive integer position. The experiment demonstrates that a position-only response and an accepted response naming an unrelated Source both cause a checkpoint.

Run `uv run python experiments/usability/hooks/run.py`. The default baseline is immutable; `--baseline` selects another explicit revision. A Git archive of the two plugins is extracted into an isolated user-cache directory. Private MCP configuration is changed only in that temporary copy to select a loopback fixture. HOME, diagnostic state, and project paths belong to the temporary directory. Resources are deleted afterward; results retain only synthetic outcome fields. Python 3.13.13 on Linux executes actual adapter subprocesses and urllib HTTP handling against a synthetic Server. This is not actual Codex/Claude host callback qualification or a real PowerContext Server run.

The independent variable is acknowledgement validation. The bounded variant changes only the capture return boundary: verify exact response fields, accepted status and matching `content` Source identity before allowing existing positive-position/checkpoint handling. Valid capture checkpoints in both variants; both malformed cases checkpoint only in baseline. Strict rejection emits `invalid_response` for `capture_source`, contains no prompt, endpoint, path or receipt body, and exits zero. The write may have happened: invalid acknowledgement must not trigger automatic replay or imply known failure to persist.

The experiment leaves Scope resolution, HTTP deadline, capture consent, native event parsing, authorization, response limits and output unchanged. Native transport code is not replaced by an SDK call. No elapsed-time or worker-performance claim is made. Codex resolves its endpoint from native MCP configuration before environment overrides; the fixture honors that source rather than inventing a shared configuration convention.

## Primary sources and compatibility

The baseline [capture response contract](https://github.com/oceanbase/powercontext/blob/f28f8edfcb2972ac322f4f12b1f224226a9a40ab/openapi/powercontext.yaml) has only `accepted` status; repeated accepted capture is not a separate `duplicate` response status. Source identity remains generated from Scope, session, native event identity when available and prompt content. Identical text without native identity can deduplicate within a session; this slice does not invent event IDs or change existing persisted identities.

[#1691 at 3e90e854](https://github.com/oceanbase/powercontext/tree/3e90e8542db8c513c02b13e6f244fa8f070983c2) is closed, unmerged implementation material. Its actual resources and target code were read through authenticated GitHub API along with PR reviews. Reviews identify global tools emitted without target selection and a descriptive operation list confused with runtime authorization. [RFC 1733](https://github.com/oceanbase/powercontext/blob/f28f8edfcb2972ac322f4f12b1f224226a9a40ab/docs/en/rfcs/1733-usability-and-agent-workflows.md) establishes common direction, not installed shared-core behavior. The isolated Claude/WorkBuddy adapters explicitly cannot import `powercontext`; adding that dependency to fix response validation would broaden installation requirements.

[Codex's native schema at e9e6cf63](https://github.com/openai/codex/blob/e9e6cf63492da108a3cabaf3cc7b23d0640ef4cf/codex-rs/hooks/schema/generated/user-prompt-submit.command.input.schema.json) includes `session_id` and required native `turn_id`. This supports consuming native identity, not assuming all hosts have it. [Claude's plugin Hook development guidance at 71cdddec](https://github.com/anthropics/claude-code/blob/71cdddec623889d38af14b7a489670a03186f659/plugins/plugin-dev/skills/hook-development/SKILL.md) keeps input/output and plugin-root wiring native. These source schemas/guides do not establish that a particular installed host version emits an event in this environment.

[Lody at 811b5733](https://github.com/LodyAI/Lody/tree/811b573329716b23e1144e5d66211ea4ddfb0dfd) delegates agent execution through provider extensions pinned as submodules; its Skill registry lists verified provider directories separately. Treating the launcher as another automatic Hook host would create a fictional lifecycle. Current [Lody Skills documentation](https://lody.ai/docs/skills/) describes discovery as read-only. Use the integration of the actual executing Agent, preserving its consent and lifecycle.

## Independent delivery contract

Validate full acknowledged Source receipts in Codex, Claude Code and WorkBuddy before advancing checkpoints. Keep automatic recall/capture failures non-blocking; retain native event/permission/configuration/output and existing no-replay behavior. Use one public loopback case catalog for exact receipt identity, missing fields, rejected status, boolean/invalid position, valid repeated acceptance and capture opt-out. Distribution may later share the tiny isolated validator as a resource; no new Client engine or daemon is required for this correction.
