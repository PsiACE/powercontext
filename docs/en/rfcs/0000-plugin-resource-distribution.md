# Summary

Provide repository build-time rendering and checking for complete native Skill resources. A declarative manifest selects shared sources and explicit host overrides for Agent Plugin, Claude Code, WorkBuddy and Codex. Generated resources retain current native guidance and reference completeness. Tools, MCP configuration, Hook registrations, credentials and qualified support remain with their existing owners.

# Motivation

Several entry files are byte-identical while native references and specialized entries differ. Universal portable copying changes Claude/WorkBuddy guidance and removes Codex's discovery metadata and Experience/Skill reference. Keeping every copy separately authored leaves a common entry edit visible only in the directly edited host. A bounded [projection experiment](https://github.com/oceanbase/powercontext/tree/f28f8edfcb2972ac322f4f12b1f224226a9a40ab) fixes baseline resource bytes; `experiments/usability/distribution/` records executable selection comparisons. Byte inspection and pure projections do not qualify native host loading.

# Guide-level explanation

Contributors author common guidance in the Agent Plugin Skill baseline and native differences in `integrations/distribution/skills/overrides/<target>/`. `skills/targets.json` maps each generated file to one source. Adding or removing workflows requires an explicit target/resource decision; a host cannot acquire tools merely because another host supports them.

`make plugin-skills-check` verifies checked-in outputs without writes and is part of `make check`. `make plugin-skills` intentionally refreshes declared repository resources. A selected complete Skill can be built independently:

```bash
uv run python scripts/generate_plugin_skills.py --target codex --output ./build-skills
```

The output is `build-skills/codex/powercontext-project-context/`. Existing native plugin packaging includes the checked-in Skill resources as before. No new runtime, source download, installer receipt or live-host synchronization is introduced.

# Reference-level explanation

## Source ownership

| Resource | Authoritative owner | Output |
| --- | --- | --- |
| Equal-contract common entry/reference | Agent Plugin Skill baseline | Explicitly selected native files |
| Different host routing, Scope or reference guidance | Target override source | That target only |
| Exposed tools and runtime semantics | Existing native adapter/API contract | Not generated by this slice |
| MCP/auth and user settings | Existing host configuration | Not read or written |
| Supported capabilities and qualification | `integrations/capabilities.toml` and maintained evidence | Unchanged |

The target manifest has schema version 1, a declared native destination, a file-to-source mapping and optional explicitly retired paths. Paths must be contained relative paths. Source resolution cannot escape the selected checkout. Each projection requires valid discoverable entry metadata and all local Markdown references, including recursively linked declared references. Additional native files such as Codex `agents/openai.yaml` remain declared resources.

## Build/check/publication

Rendering resolves the complete selected resource set in memory before inspecting any destination. Check mode reports missing or differing declared files and existing retired files, returns nonzero on drift and does not write. Output mode writes separate complete Skill directories for selected targets; fixed source bytes and manifest yield identical file bytes.

Repository refresh stages each changed file beside its destination and replaces it individually after validating every selected projection and path. Only declared files can be replaced, and only explicit `retired` paths can be removed. Unrelated files remain. Symlink destinations are rejected before publication. `--write` is an intentional developer update of generated repository content, not a promise to preserve modifications to declared generated files in a deployed user plugin. There is no persistent hash ledger or complete-tree transaction; interruption can leave partial repository refresh, detected and repaired by rerunning check/render.

Private MCP configuration, plugin manifests, native hooks and runtime dependencies are outside the ownership set. Source selection is the developer's Git checkout; the renderer neither chooses nor executes remote build rules. Existing package and plugin release versions remain independent under current release policy. Reproducible bytes alone do not authenticate a publisher or establish runtime compatibility.

## Acceptance

The focused suite builds each declared native Skill into two isolated directories and compares complete file digests. It verifies current checked-in resource equality, missing Experience/Skill reference rejection, drift reporting, explicit stale-file retirement, preservation of foreign files/private MCP settings, contained paths and symlink rejection. Generated Skill discovery in actual Agents remains separate native qualification. No generator performance or runtime support claim follows from these filesystem tests.

# Drawbacks

Build-time source ownership adds a manifest and override directory. Contributors must update declared reachability when references change. Host differences still require native authoring; overgeneralized templates would conceal those differences. Checked-in outputs occupy space but support existing direct source loading and packaging without a new runtime dependency.

# Rationale and alternatives

An explicit file projection shares proven equal contracts and preserves differences. A universal baseline or global tool catalog changes public surfaces, as demonstrated by the bounded comparison and #1691 review. A runtime deployment ledger or bidirectional user-file synchronization adds ownership and recovery semantics that repository generation does not need. Content-only conformance detects drift, but without a common source it still requires repeated edits; rendering supplies the missing propagation operation.

# Prior art

[#1410](https://github.com/oceanbase/powercontext/pull/1410) defines deterministic resource projections without making capability parity a prerequisite. Closed, unmerged [#1691](https://github.com/oceanbase/powercontext/pull/1691) supplies implementation material; its actual generator and reviews expose universal tool emission and unsupported authorization assumptions. Those behaviors are excluded here.

[Magpie's owned Skill copies](https://github.com/yetone/magpie/blob/23d9e5def8c5595c7a8a49df8f2a376084980927/internal/library/skills.go) and [edit-preservation tests](https://github.com/yetone/magpie/blob/23d9e5def8c5595c7a8a49df8f2a376084980927/internal/library/skill_edits_test.go) demonstrate why installed user-file synchronization needs stronger ownership semantics. [Lody's directory registry and tests](https://github.com/LodyAI/Lody/blob/811b573329716b23e1144e5d66211ea4ddfb0dfd/packages/shared/tests/acp-skills.test.ts) retain provider-specific verified discovery. This slice adopts explicit ownership and native discovery boundaries, without claiming either system's real-host execution here.

# Unresolved questions

No runtime or release-format decision is needed for these Skill projections. A future live installation updater must define user-edit conflicts, rollback and authenticated distribution independently. Additional host formats require a maintained target selection and native evidence.

# Future possibilities

Declare more hosts after preserving their current guidance and resource contracts. Share small isolated execution resources only where deployment and failure semantics match. Generate tool schemas or registrations only with explicit target selection and a separately verified public capability contract.
